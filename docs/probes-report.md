# 技术探针结论

三条一次性探针，验证同一个问题：**两路分离的音视频流，能不能在客户端合成播放**。
探针代码已弃，结论已经变成正式实现，留这份记录是为了下次遇到同类问题不必从零再验。

| 探针 | 问题 | 结论 | 落在哪 |
|---|---|---|---|
| **P1** | libvlc 能否把**本地** `video.m4s` + `audio.m4s` 用 `:input-slave` 合成播放 | 通过 | Client `PlaybackEngine` 的 `dual` 分支 |
| **P2** | 同上，但两条流走 **HTTP**（服务端 Range 代理） | 通过 | 同上；并确证 Avalonia 能嵌 libvlc |
| **R1** | Android Media3 能否直读 HTTP fMP4 双流并 seek | 通过 | Android `MergingMediaSource` |

判定线是「**视频与音频两个解码计数器都在涨 + 位置在推进**」，不是「画面看起来像在放」。
`:input-slave` 最典型的失败是音频静默不进来、画面照常——只看画面会误判成通过。

## 对实现的净影响

1. 客户端合成双流成立 → 服务端不为播放转码，`ffmpeg remux` 只作解码失败时的兜底
2. Avalonia + libvlc 成立 → PC 客户端可做真正的横屏播放器，不必迁就浏览器限制
3. Media3 直读成立 → APK 不必先把 m4s 拼成 mp4
4. 三端都**不依赖 ffmpeg 就能播**（ffmpeg 只用于封面抽帧与兜底 remux）

## 两条必须记住的坑

- **探针通过 ≠ 版本可用。** media3 1.5.1 探针全绿，正式使用中却发现它对 HEVC 的 `hvcC` 解析有 bug，
  表现为有音无画；换 1.11.1 又要求 `compileSdk 36`。最终锁 **media3 ≥ 1.9.0**。
  教训：探针只证明「这条路通」，证明不了「这个版本在所有编码上都能用」，样本编码要单独记。
- **`inputBitrate=0.00` 是无害的。** libvlc 对 m4s 这类无索引容器不统计入向码率，
  不能拿它当「没在下载」的证据。
